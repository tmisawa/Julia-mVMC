Timing and Monte Carlo contracts

Each elapsed measurement wraps a complete public optimization or PhysCal runner: input parsing, parameter/state setup, initialization, Monte Carlo, observables, SR in Opt, ordinary synchronization and final results/output. CPU output files are included; the GPU returns numerical arrays and final summaries instead of those files. Fixed PhysCal checkpoint preparation is outside timing. GPU timing synchronizes before and after the public call. MPI timing reports the maximum rank wall time; the preceding barrier, subsequent timing/status allreduces and the driver's extra PhysCal energy-file readback are outside the clock. MPI collectives and the replicated direct SR solve performed by the public runner remain inside timing.

CPU uses one sequential SFMT chain per group with the existing base+group seed convention. GPU uses independent XORWOW walkers, legal empty-destination proposals and resident rank updates. Their trajectories, burn-state reuse, accepted moves and initial warmup work differ. Equal retained samples and SR steps do not establish equal effective sample sizes. No cross-backend trajectory or bitwise floating-point equality is claimed.

Sampling and output scope

The CPU runner uses one sequential SFMT chain, stores 300 thinned configurations, and reuses its burn state. The GPU runner uses 300 independent XORWOW chains, performs an initial warmup for every chain, and takes one configuration from each chain per batch. Both select empty hopping destinations for this nonlocal-spin, half-filled input. They have different RNG streams/draw semantics and initial configurations.

Configured attempted-proposal budgetCPUGPU
Optimization, including warmup770,560806,400
PhysCal, including warmup38,52876,800

CPU's first sampling call uses (warmup + samples) × interval × Nsite attempts; later calls use (samples + 1) × interval × Nsite. GPU uses walkers × (warmup × interval × Nsite + batches × interval × Nsite). For this pure-hopping input with no local-spin sites and available empty destinations, every configured proposal has a legal candidate; that is a model/proposal deduction, not a measured counter. These counts are not effective sample sizes. Full accepted/valid counters are not exposed by the public runners. GPU's final interval accepted 13,994 moves in optimization and 14,325 in PhysCal in every repetition; these are only final-interval counts.

The CPU public runners write C-format per-step/final parameter, energy and Green files. GPU runners return numerical arrays and resident state, with their final summaries/transfers included in GPU timing; equivalent C-format files are not written. CPU PhysCal energy-file readback and the benchmark's acceptance/finite-result checks happen after the timed runner call. The displayed ratios therefore measure the documented runner lifecycles, not equivalent RNG trajectories or proven effective-sample throughput.

Warmed inner-loop transfer audit

A separate GPU 0 CUPTI audit excluded setup and compilation, warmed one complete production optimization iteration, and profiled two subsequent 300-walker iterations through sampling, observables, derivatives, SR, parameter gauge, Slater refresh and sampling-cache refresh. Final solver-status, energy-history and parameter readbacks occurred after profiling. This is a transfer audit, not an additional GPU throughput result.

The profiled application boundary contained 12 host-to-device copies, zero device-to-host copies, and two device-to-device copies. Consequently, this measured pre-follow-up source had residual H2D traffic. H2D copy activity totaled 7.63 microseconds on the device; the corresponding host API activity totaled 85.35 microseconds across two iterations. The profiled final parameters were finite. The raw CUPTI log preserves the copy names and counts; the developer script is /tmp/profile-julia-whole-inner-loop.jl. Scalar uploads from generic numerical-library wrappers are suspected, but this audit alone does not attribute each transfer to its caller.

Resident SR moments follow-up

Phase-level CUPTI probes located all six uploads per iteration: two scalar arguments for each of the OO and HO products, and two for CUDA's GEAM-based matrix subtraction. Mean reductions and the outer product uploaded no scalars; native cuSOLVER uploaded none. The production follow-up reuses the SR workspace's resident alpha/beta pointers for OO and HO and performs elementwise covariance subtraction, preserving the existing outer-product calculation and division order. The generic implementation remains an independent GPU reference.

After that change, the same warmed two-iteration host-side audit recorded zero H2D, zero D2H, and two D2D application copies, with finite final parameters and unchanged reported energy history. The follow-up raw CUPTI log preserves this result. Ten independent CPU/generic-GPU moment comparisons, five native-solver checks and sixteen complete L128 runner checks passed without relaxing tolerances. These are host-side correctness/transfer checks; the earlier elapsed-time tables measure the preceding source and are not reattributed to this change or to the Dev Container.

Adopted changes and transfers

The real Pfaffian assigns columns to warps, preserves pivot/product order, and uses explicit round-to-nearest multiply/add/divide operations. Slater updates use C's four spin-block expressions directly, with resident parameter indices, signs and rotation coefficients. Large inverse batches use cached device pointer tables for cuBLAS LU/inversion and enforce skew symmetry before use.

Only unoccupied Slater columns need batched GEMM; occupied columns satisfy A^-1*S_occ=-I. Ordinary operators evaluate independently against read-only virtual moves, followed by Hamiltonian addition in original input order. Large analytic derivatives use resident CSC coefficients and predecoded row coordinates, directly contracting inverse cofactors. Singular projection sectors retain exact minor evaluation with disjoint fallback workspaces.

The single-device warmed sampling+observable+derivative CUPTI application range records zero memory-copy records, including device-to-device copies. Profiler bookkeeping before its initial synchronization is excluded using the same range as CUDA's display. Two-device results are copied only after timing; their worker protocol does not transfer configurations or intermediate results between GPUs. Setup still constructs and uploads the dense Slater basis, so startup cost and memory capacity remain relevant. Each production optimizer/PhysCal runner uses one device; the two-device script shards only the fixed measurement workload.
